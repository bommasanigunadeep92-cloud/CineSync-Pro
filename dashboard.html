Threads and Multithreading

Simultaneous Customer Execution with Independent Program Counters
Foundation
1. Formal Definition
A thread is the smallest sequence of programmed instructions that can be managed independently by an operating system scheduler. Multithreading allows a single process to execute multiple execution flows concurrently, sharing the process's code, data, and resources while maintaining individual stacks and registers.
2. Why It Is Required
In a commercial cinema ticketing platform, thousands of customers attempt to book tickets simultaneously. Single-threaded architectures force customers to wait in a linear queue, causing unacceptable latency and server timeouts. Multithreading allows each customer to be served in their own thread concurrently.
3. How It Works Internally
The OS kernel allocates a Thread Control Block (TCB) for each thread containing its Thread ID, Program Counter (PC), CPU registers, and stack pointer. Threads share the process heap and open file descriptors. The OS scheduler preempts and time-slices CPU cores between threads.
4. CinemaPro Usage
When customers initiate ticket bookings, CinemaPro spawns separate Python threads (Customer-1, Customer-2, Customer-3) via Python's threading.Thread(target=process_booking).

Concurrency & Interleaving

Simultaneous Incoming Requests & Non-Deterministic Execution
Execution
1. Formal Definition
Concurrency is the execution of multiple instruction sequences at the same time. On a single-core CPU, concurrency is achieved through interleaving via rapid context switches. On multi-core CPUs, concurrency is achieved through true parallel hardware execution.
2. Why It Is Required
When online bookings open for premier shows (e.g., Oppenheimer 70mm), hundreds of booking requests hit the web server in the exact same millisecond. The server must handle all incoming connections concurrently rather than serializing them.
3. How It Works Internally
The OS CPU scheduler uses preemptive algorithms (e.g., Round Robin, Completely Fair Scheduler). A timer interrupt triggers context switching, swapping CPU register state between threads without warning. Consequently, instruction order across threads is non-deterministic.
4. CinemaPro Usage
CinemaPro uses threading.Barrier(N) to hold multiple customer threads until all are ready, releasing them simultaneously to simulate realistic concurrent burst traffic against the booking endpoint.

Race Condition – Without Mutex

Time-Of-Check to Time-Of-Use (TOCTOU) Flaw & Double-Booking Hazard
Unsynchronized Hazard
EDUCATIONAL HAZARD DEMONSTRATION ONLY: Runs without synchronization on isolated sandbox seat SIM-RACE. Real customer seats in the database are 100% protected.
1. Formal Definition
A race condition is an undesirable situation where the system's output or final state depends on the uncoordinated timing, interleaving, or sequence of other uncontrollable events. It arises when two or more concurrent threads access shared data and at least one attempts to write.
2. Why It Is Required to Understand
Without seeing a race condition in action, students cannot appreciate why Mutex locks are worth their synchronization overhead. Double-booking is the textbook real-world cinema catastrophe caused directly by a race condition.
3. How It Works Internally (TOCTOU)
Time-Of-Check to Time-Of-Use (TOCTOU) gap:
1. Thread A checks database: is_booked == 0 (Seat is available).
2. Context switch occurs. Thread A pauses for payment verification.
3. Thread B checks database: is_booked == 0 (Seat still looks available!).
4. Thread B books seat and writes is_booked = 1.
5. Thread A wakes up, assumes seat is still free based on its earlier check, and writes is_booked = 1.
Outcome: Two confirmed tickets issued for the exact same seat!
4. CinemaPro Usage
CinemaPro provides an un-synchronized educational simulation endpoint (POST /api/lab/race-demo) that bypasses locks, introduces an artificial context switch delay (0.05s), and registers double-booking collisions.

Critical Section Architecture

Dijkstra's Synchronization Rules: Entry, Critical, Exit & Remainder Sections
Architecture
1. Formal Definition
A critical section is a piece of code that accesses shared resources (such as common variables, database records, or hardware devices) that must not be accessed concurrently by more than one thread of execution.
2. Why It Is Required
To prevent data corruption, any solution to the critical section problem must satisfy Dijkstra's three requirements: 1. Mutual Exclusion: If thread A is in CS, no other thread can enter. 2. Progress: If no thread is in CS, selection cannot be postponed indefinitely. 3. Bounded Waiting: A bound must exist on the number of times other threads enter before a waiting thread enters.
3. How It Works Internally
Every critical section protocol is partitioned into 4 distinct phases:
1. Entry Section: Requests permission to enter (e.g., lock.acquire()).
2. Critical Section: Reads and updates shared seat records.
3. Exit Section: Relinquishes ownership and signals waiters (e.g., lock.release()).
4. Remainder Section: Executes independent code (e.g., formatting invoice, sending email).
4. CinemaPro Usage
In app.py, the SQL query verifying seat availability followed immediately by UPDATE seats SET is_booked = 1 is the protected Critical Section.

Mutex Lock – With Mutex (Week 2 PDF)

Real Python threading.Lock() Guaranteeing Mutual Exclusion
Week 2 PDF Core
1. Formal Definition
A Mutex (Mutual Exclusion) is a binary synchronization primitive used to protect shared data from simultaneous access. Only one thread can hold the lock at any point in time. Any other thread attempting to acquire the lock is blocked and suspended until the current owner releases it.
2. Why It Is Required
Mutex is the fundamental solution to race conditions. By ensuring that only one customer thread can execute the seat check and reservation update, double-bookings are guaranteed to be 100% mathematically impossible.
3. How It Works Internally
In Python, threading.Lock() is implemented at the C-extension layer using OS-level mutexes (e.g., Windows CRITICAL_SECTION or POSIX pthread_mutex).
• acquire(blocking=True): If state is UNLOCKED, sets state to LOCKED and caller continues immediately. If state is LOCKED, thread transitions from RUNNING to BLOCKED and is placed in the lock's wait queue.
• release(): Sets state to UNLOCKED and signals the OS kernel to wake the first thread from the wait queue.
• with lock: Context manager syntax guaranteeing release via internal __enter__ and __exit__ (try-finally).
4. CinemaPro Usage
In app.py, CinemaPro instantiates booking_mutex = threading.Lock(). Every live booking route wraps database operations with with booking_mutex:.

Counting Semaphore (Week 3 PDF)

Real Python threading.Semaphore(N) with Configurable Capacity
Week 3 PDF Core
1. Formal Definition
A Semaphore is a protected variable or abstract data type that constitutes the classic method for restricting access to shared resources in a multi-processing environment. A Counting Semaphore maintains an integer counter initialized to $N$, representing the total number of available permits.
2. Why It Is Required
While a Mutex permits only 1 thread at a time, a cinema backend can safely handle $N$ concurrent transactions across different screens without overloading SQLite or saturating server connection pools. Semaphores provide controlled resource throttling.
3. How It Works Internally
A counting semaphore consists of an integer counter and a wait queue:
• wait() / acquire(): Decrements the counter. If counter $\ge 0$, thread proceeds. If counter $< 0$, thread blocks and enters the semaphore wait queue.
• signal() / release(): Increments counter. If counter $\le 0$, wakes a waiting thread from the queue.
• When initialized with $N=1$, it functions as a Binary Semaphore (equivalent to a Mutex).
4. CinemaPro Usage
CinemaPro backend initializes concurrency_semaphore = threading.Semaphore(3). Every incoming booking request must acquire a permit before beginning its checkout transaction.

Thread Joining (thread.join())

Parent Process Synchronization & Aggregating Parallel Results
Barrier Sync
1. Formal Definition
Thread joining is a synchronization mechanism where one thread pauses its execution and blocks until one or more target threads finish executing and terminate. In POSIX and Python, this is accomplished via pthread_join() or thread.join().
2. Why It Is Required
When a parent process delegates subtasks (such as calculating group seat discounts, validating credit card payments, and reserving seats in parallel), it cannot calculate the final total or issue a receipt until all worker threads complete. Calling .join() prevents race conditions on aggregate results.
3. How It Works Internally
Calling t.join() suspends the calling thread. The OS transitions the caller to the BLOCKED state and stores it in the target thread's join queue. When the target thread terminates, its exit handler cleans up its TCB and signals the OS to wake all joined threads back to the READY state.
4. CinemaPro Usage
CinemaPro backend spawns 3 parallel workers for group booking validation (Member-A, Member-B, Member-C), calls t.join() on each, and then compiles the final aggregated confirmation receipt.

Shared Data & Resource Management

ACID Atomicity, SQLite Concurrency & Memory State Coherency
Data Integrity
1. Formal Definition
Shared data is information stored in shared memory address spaces or persistent storage that is readable and writable by multiple concurrent processes or threads. Resource management governs access protocols to prevent dirty reads, torn writes, and deadlocks.
2. Why It Is Required
In group ticket bookings where 3 or 4 seats are reserved together (e.g., A1, A2, A3), the system must guarantee Atomicity: either all requested seats are booked, or none are booked. A partial failure must cleanly roll back to prevent orphaned seat allocations.
3. How It Works Internally
CinemaPro uses Write-Ahead Logging (WAL) and explicit SQLite database transactions. Combined with Python memory synchronization locks, it ensures that memory mirrors the disk state consistently without cache coherency anomalies.

Observed Difference & Scientific Explanation (Step 6 Comparison)

1. Booking Without Mutex: Multiple uncoordinated customer threads execute interleaved check-then-act sequences across the shared SQLite database. Within the Time-Of-Check to Time-Of-Use (TOCTOU) gap, multiple threads simultaneously observe the seat as is_booked = 0, resulting in conflicting double-bookings.
Important Clarification: A race condition does NOT always produce duplicate bookings on every single run; duplicate bookings are an unpredictable, non-deterministic hazard resulting from uncoordinated thread interleaving and CPU scheduling.

2. Booking With Mutex: Python's threading.Lock() establishes strict binary Mutual Exclusion. Only one customer thread enters the Critical Section to check availability and write the reservation. Competing threads find the seat occupied and are safely rejected, guaranteeing exactly 0 collisions and 100% database integrity.

3. Booking Using Semaphore: Python's threading.Semaphore(N) enforces controlled throughput by allowing up to $N$ concurrent transactions to execute simultaneously. Surplus customer threads wait gracefully in the queue until an active thread releases its permit, preventing server connection pool exhaustion.

University Viva / Faculty Review Guide

What is a Mutex Lock?

A Mutex (Mutual Exclusion) lock ensures that only one thread can execute a critical section at any given time. In this application, checking seat availability and booking seats is enclosed in a Mutex block (with booking_mutex:) to prevent race conditions.

What is a Counting Semaphore?

A Counting Semaphore maintains a counter representing available permits. It allows up to $N$ concurrent threads to proceed simultaneously (here, $N=3$). Once all permits are exhausted, subsequent threads must wait in queue until a permit is released.

What is a Race Condition?

A race condition occurs when two or more threads access shared resources and try to modify them concurrently. Without synchronization, Thread A checks seat A5 (finds it free), pauses for payment processing, while Thread B checks seat A5 and books it. Thread A then finishes and also books seat A5, resulting in double-booking.

How does Group Booking maintain Atomicity?

Group booking allocates multiple seats (e.g. A1, A2, A3) together. If even one seat in the group is already booked, the entire transaction rolls back cleanly, adhering to ACID atomicity principles.
